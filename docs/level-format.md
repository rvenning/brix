# Level format

Levels are JSON documents in the `brix-level/1` format, defined in
[`src/levels/format.ts`](../src/levels/format.ts). The same format is used for the
112 original levels, for levels made in the editor, and for imports/exports.

## Why it looks like this

The original `LEVELS` file stores each problem as a 178-byte record: a 14×12 tile
grid (row-major, one byte per cell) followed by 10 metadata bytes. The canonical
format keeps **everything the record contains**, including bytes the original
ignores, so a canonical level encodes back to the identical 178 bytes. That is
what makes "112 / 112 exact" checkable rather than asserted.

It also keeps the grid **as stored, not as loaded**: the original's loader writes
the elevator tile at the elevator's position, overwriting the grid. Level 88
depends on this — its grid has an empty cell where its elevator appears.

## Example

```json
{
  "format": "brix-level/1",
  "id": "original-005",
  "number": 5,
  "origin": "original",
  "tree": { "level": 2, "choice": 1, "problem": 1 },
  "width": 14,
  "height": 12,
  "tiles": [
    "              ",
    "      ####    ",
    "      #.1#    ",
    "     #=.2#    ",
    "    #=.3=#    ",
    "    #..=#     ",
    "   #=..#      ",
    "  #=..=#      ",
    "  #12=#       ",
    "  #3E#        ",
    "  #==#        ",
    "  ####        "
  ],
  "cursor": { "x": 7, "y": 2 },
  "elevator": { "x": 4, "y": 9, "direction": -1 },
  "timeLimit": { "minutes": 1, "seconds": 0 },
  "original": { "offset": 712, "elevatorDirectionByte": 1, "secondaryElevator": [0, 0, 0] }
}
```

## Fields

| Field | Meaning |
|---|---|
| `format` | Always `brix-level/1`. |
| `id` | Stable identifier. Originals are `original-001` … `original-112`; editor levels are `custom-…`. Progress is stored by id. |
| `number` | 1–112 for originals (file order), 0 for custom levels. |
| `origin` | `original` or `custom`. The editor opens originals read-only. |
| `name` | Optional display name (custom levels). |
| `tree` | Originals only: position in the level tree. Level *n* has *n* choices of 4 problems. `tree.level` scales the clear and time bonuses. |
| `width`, `height` | Board size in cells. Originals are 14×12; custom levels may be 4–24 × 4–20. |
| `tiles` | `height` strings of `width` characters, top row first (see below). |
| `cursor` | Where the cursor starts. |
| `elevator` | `null`, or the elevator's cell and starting direction: `-1` up, `1` down, `0` never moves. |
| `timeLimit` | Displayed minutes and seconds. A BRIX second lasts 21 BIOS ticks ≈ 1.153 s. |
| `original` | Originals only: bytes needed for an exact round trip (file offset, the raw direction byte, and the unused second-elevator bytes 5–7). |

## Tile characters

| Char | Byte | Tile |
|---|---|---|
| `.` | `00` | empty |
| `1`–`8` | `01`–`08` | block of that type |
| `=` | `0A` | inner wall (solid; the cursor may cross it) |
| `#` | `0B` | frame wall (solid; the cursor stops at it) |
| `E` | `0C` | elevator tile as stored in the grid (the loader places the elevator from `elevator`, not from this) |
| ` ` (space) | `0D` | void, outside the playfield |

## Mapping to the original record

| Record bytes | Canonical field |
|---|---|
| 0–167 | `tiles[y][x]` = byte `y*14 + x` |
| 168, 169 | `cursor.x`, `cursor.y` |
| 170, 171 | `elevator.x`, `elevator.y` (an elevator exists only if both are non-zero) |
| 172 | `elevator.direction` via the loader's rule: `0` → 0, `1` → −1, anything else → +1; raw value in `original.elevatorDirectionByte` |
| 173–175 | `original.secondaryElevator` (unused by every original level) |
| 176, 177 | `timeLimit.minutes`, `timeLimit.seconds` |

## Level packs

`public/levels/original/levels.json` is a `brix-level-pack/1` document with the SHA-256
of the source `LEVELS` file and all 112 levels in order. The game loads the pack; the
per-level files beside it are the reviewable canonical copies. Both are generated by
`npm run extract-levels` and checked by `npm run validate-levels`.

## Rules for custom levels

`lintLevel()` rejects structurally broken levels (wrong row lengths, unknown characters,
cursor off the board). The editor also warns about playable-but-doomed designs: no
blocks, a single block of a type, blocks on the outer rows (never scanned by the rules),
or a start position on a frame wall.
